I attempted to disprove correctness across all four lenses, with primary focus on concurrency/ordering per the trigger. I found one concrete, high-severity race in the supersession write path that survives all currently-green tests (confirmed there is zero dedicated test coverage of association.ts or association-write.ts).

## Finding: out-of-order concurrent writes let a supersession regress to a stale run

Mechanism. scenario.ts rule 2b decides whether to supersede by comparing a freshly-recovered candidate against the association snapshot read at the start of that single request. That decision is fixed early in the request, well before the request's slow async work (git subprocess calls in resolveIterateContext) has run.

The actual write, supersedeMissionContext (server/src/core/mission-context/association.ts:97-108), did NOT re-validate recency against the store's current value at write time -- it only checked that a missionContext existed and that association.source === "transcript_run_id", then unconditionally overwrote.

Concrete reproduction (multi-tab is explicitly a supported pattern per CLAUDE.md Architecture rule 4, "multi-tab for free"):
1. Task has stale missionContext = R1.
2. Poll A reads transcript containing footers up to R2; detectScenario fixes associateRunId = R2 (proven newer than R1). A's request then does slow git I/O before reaching the write.
3. Poll B (a second tab, or the next 1s tick, landing before A has written) reads task.missionContext -- still R1 -- but the transcript has grown further and now contains a footer for R3. B fixes associateRunId = R3 (proven newer than R1). B's git calls happen to be fast; B writes R1 -> R3 and persist() succeeds. Store now correctly holds R3.
4. A finally resumes and writes. Because the previous implementation re-read task.missionContext fresh at write time (which now shows R3) and only compared "does my target differ from current", the guard would pass and A would overwrite R3 back to R2.

Result: the durable association silently regresses from the correct, newer run (R3) to a staler one (R2), purely due to async scheduling order -- the exact class of bug ("a stale association never refreshes") this diff exists to fix, reintroduced one level deeper. Notably this bug requires no failure at all -- both writes succeed; it is a plain lost-update/TOCTOU race, which is arguably worse than the ELOCKED case the code already guards against.

What would resolve it: have supersedeMissionContext re-validate against the store's CURRENT value at write time using the value the CALLER actually decided against (not a fresh re-read) -- i.e. true compare-and-set semantics.
