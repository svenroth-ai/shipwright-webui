# Doubt Review — Stage 3 (Org Page, iterate-2026-08-26-org-page)

I attacked along all four lenses, weighted toward **boundary & contract** (the charter-write authorization gate) and **reversibility** (the PUT write path), with secondary passes on **concurrency & ordering** (AuditLogModal) and a spot-check of hidden coupling. I did not have shell access in this sandbox, so I worked from direct file reads rather than a unified diff — I read every file the task named plus the Hono routing/request internals that turned out to be load-bearing for the main finding below.

## Finding 1 (HIGH, boundary & contract + reversibility) — the `requireChartLead` gate on the charter PUT can be bypassed with a URL-encoded trailing slash, letting a write reach an unregistered/orphaned lead's `charter.md`

This is the same authorization gap the External-Code-Review HIGH finding #1 was written to close ("any syntactically valid, never-registered lead id could... have a charter.md written... with no corresponding org-chart.json entry"). The fix as shipped only closes it for the *literal* string the request handler sees; it reopens the moment the raw `leadId` and the *normalized* `leadId` disagree.

**The mechanism, traced through the actual code:**

- `server/src/routes/org.ts:170-213` (PUT handler): `const leadId = c.req.param("leadId")`, then `relpath = ${leadId}/charter.md`, then `resolveOrgAllowlistedTarget(leadsRoot, relpath)` (`server/src/external/org/_helpers.ts:154-184`), then — only if `target.kind === "charter"` — `requireChartLead(c, leadId)` at `routes/org.ts:198`.
- `requireChartLead` (`routes/org.ts:123-138`) deliberately no-ops when the RAW `leadId` fails `LEAD_ID_RE` (`if (!LEAD_ID_RE.test(leadId)) return { ok: true }`), on the stated assumption that "a shape-invalid leadId is left to the target core's own 400" (comment at line 120-122).
- That assumption is true for the sibling GET routes (`lead-doc-read.ts:47`, `audit-log.ts:67` both re-check `LEAD_ID_RE` on the *same raw string* and 400 before touching the filesystem) — but it is **false** for the charter PUT path, because `resolveOrgAllowlistedTarget` doesn't validate the raw string at all; it derives its own, more lenient "leadId" by slicing the **path.resolve-normalized absolute path** (`_helpers.ts:166-181`) and testing *that* against `LEAD_ID_RE`. `path.resolve` silently collapses redundant `/` characters, so a raw `leadId` with a trailing slash normalizes away.
- Hono's router adds the missing ingredient: `getPath()` (`server/node_modules/hono/dist/utils/url.js:68-85`) decodes the request path with `decodeURI`, which — unlike `decodeURIComponent` — leaves `%2F` **encoded** (`/` is a reserved character `decodeURI` won't touch). Route segmentation (`splitPath`, same file, lines 2-8) therefore treats `ghost-lead%2f` as **one** path segment, matching `:leadId` as a single param. Only later, when the handler calls `c.req.param("leadId")`, does Hono apply `tryDecodeURIComponent` (`request.js:45-52`), which **does** decode `%2F` into a real `/`. Net effect: a single URL segment `ghost-lead%2f` becomes the string `"ghost-lead/"` inside the handler.

**Concrete exploit:** `PUT /api/org/leads/ghost-lead%2f/charter` with body + `If-Match`.
- `leadId` (closure var, raw) = `"ghost-lead/"`.
- `relpath` = `"ghost-lead//charter.md"` → `resolveOrgAllowlistedTarget` → `pathGuard` collapses the double slash → normalized leadId extracted = `"ghost-lead"` (clean) → `target.ok = true, kind = "charter"`.
- `requireChartLead(c, "ghost-lead/")`: `LEAD_ID_RE.test("ghost-lead/")` is `false` (trailing `/` isn't in the character class) → **returns `{ ok: true }`, skipping the `Object.hasOwn(chart.body.leads, leadId)` membership check entirely** — even though the codebase's own regression test (`server/src/routes/__tests__/org.test.ts:226-237`) proves `"ghost-lead"` (unencoded) is correctly 403'd as `unknown_lead` when it isn't a chart entry.
- The handler proceeds to `orgFileWriteCore` (`file-write.ts:92-172`) with the same unnormalized `relpath`; it independently re-resolves the same clean target and — since `charter` isn't a locked kind — calls `performWrite` directly (`file-write-core.ts:22-109`), which has **no chart-membership check at all**, only `lstat` (file must already exist) + `If-Match` fingerprint match.

**Practical impact:** the write only *succeeds* (rather than 404ing) when `leadsRoot/ghost-lead/charter.md` already exists on disk despite `ghost-lead` no longer being (or never being) an `org-chart.json` entry — i.e. exactly the "decommissioned/orphaned lead directory left on disk" scenario the Stage-2 LOW finding named for the GET routes. That precondition is realistic: nothing in this codebase deletes a lead's directory when it's removed from the chart. Even absent a pre-existing file, the bypass still leaks membership information (403 `unknown_lead` vs 404 `not_found`), which the fix's own contract says should be uniform. And the fingerprint needed for `If-Match` is trivially obtainable first via `GET /api/org/file?path=ghost-lead/charter.md`, which is intentionally ungated on chart membership (same allowlist the pre-existing secret-gated route already exposed).

The existing regression test for this exact HIGH finding (`org.test.ts:226`) uses a clean, unencoded `"ghost-lead"` and would not catch this — the vulnerable class is specifically "raw route-param string vs. path-normalized string disagree," which only a URL-encoded-slash probe exercises. The secret-gated family (`external/org/routes.ts`) doesn't have this shape at all — its PUT is a `path=` query-string route, not a `:leadId` route-param — so this gap is specific to the new `/api/org/leads/:leadId/charter` surface this iterate introduces.

**What would resolve it:** validate `LEAD_ID_RE` against the leadId `resolveOrgAllowlistedTarget` actually resolved to (i.e. `target.absolute`-derived), not the raw `c.req.param()` string — or simplest: have `requireChartLead` treat a `LEAD_ID_RE` failure on the raw string as "reject", not "defer", for the PUT route specifically (the "defer to downstream" reasoning only holds for GET routes whose cores re-validate the *same* raw string). Also worth adding a chart-membership check inside `performWrite`/`orgFileWriteCore` itself as defense in depth, so this class of gate can't be bypassed again by a third caller of the same core.

## Finding 2 (MEDIUM, concurrency & ordering) — `AuditLogModal`'s pagination has two related gaps under rapid interaction

`client/src/components/org/AuditLogModal.tsx:47-65, 123-135`.

1. **Rapid double-click on "Load older" can append a duplicate cursor.** The button's `disabled={isFetching}` (line 126) reflects the *previous* render's `queries` state; when a new cursor is pushed via `setCursors`, the newly-added `useQueries` entry doesn't necessarily report `isFetching: true` until at least one more render/effect cycle (TanStack Query schedules the fetch post-commit). Two click events landing inside that window both execute `onClick` against the same closure-captured `lastQuery`, so `setCursors(prev => [...prev, lastQuery?.data?.nextCursor ?? undefined])` runs twice with the same `nextCursor` value, producing `cursors` like `[undefined, 50, 50]`. `useQueries` then holds two entries with the identical `queryKey` (`["org","lead-audit",leadId,50]`); react-query dedupes the actual network call, but `entries = queries.flatMap(...)` (line 65) renders that page's rows **twice**, and the duplicate persists in local state until the modal is closed.
2. **Errors on any page after the first are invisible.** `error = queries[0]?.error` (line 59) reads only the *first* query's error state. If a later "Load older" fetch fails (network blip, transient 5xx), no error UI renders — the existing entries just sit there, `hasMore` stays `true` because `lastQuery.data` is `undefined` (line 62), and the button re-enables once `isFetching` settles. Clicking it again computes `lastQuery?.data?.nextCursor ?? undefined` — since the failed query has no `data`, this falls back to `undefined`, which is the **same key as page one**, silently re-fetching (or re-rendering, if cached) the first page into a new slot instead of retrying the page that actually failed, with no indication to the user that anything went wrong.

Neither is a security or data-corruption issue (GET-only, and react-query's cache dedup prevents a real double-fetch in case 1), but both are genuine, reachable UI-correctness bugs under exactly the interaction patterns I was asked to doubt.

**What would resolve it:** derive `hasMore`/button-eligibility from `cursors.length`/pending state rather than only `isFetching`, or disable immediately via a local "pending click" flag set synchronously in the handler; and surface/attempt retry per-page (e.g. `error = queries.find(q => q.error)?.error`, or render a per-page retry affordance) rather than only inspecting `queries[0]`.

## What I checked and found sound (attempted disproof, came up empty)

- **`pathGuard`/`realPathGuard` chain** (`server/src/core/path-guard.ts`) — pre-existing, shared infrastructure; string-based traversal check followed by a realpath-based symlink re-check, consistently applied. The **open-with-`O_NOFOLLOW`-first, `fstat`-on-the-same-fd, `realPathGuard`-after** pattern is correctly and consistently used across `file-read.ts:81-134`, `lead-doc-read.ts:56-96`, `audit-log.ts:76-116`, and `org-chart-lookup.ts:61-104` — this closes the classic separate-lstat-then-separate-read TOCTOU CodeQL flagged, and the reordering vs. `realPathGuard`'s existence requirement correctly fixes the External-Review finding #4 (missing-file 400→404). I looked hard for a residual intermediate-directory-symlink race between `open()` and `realPathGuard()`'s independent `realpathSync` call (since `O_NOFOLLOW` only blocks the *final* path component, not an ancestor directory being a symlink) — that race is real in the abstract but requires an attacker with filesystem write access to `leadsRoot` racing a symlink swap in a sub-microsecond window, which is not a threat this app's trust model (local-first, no multi-tenant filesystem) needs to defend against, and it's identical to the pre-existing pattern already accepted for the sibling `external/org/*` routes — not a new regression from this diff.
- **`Object.hasOwn(chart.body.leads, leadId)`** (`routes/org.ts:131`) — safe. `parseOrgChart`/`orgChartCore` (`org-chart.ts:49-76, 97-141`) structurally guarantee `leads` is a plain object, never an array (the External-Review MEDIUM fix for the array-vs-object confusion is real and correct — `typeof [] === "object"` is explicitly guarded with `Array.isArray`). `Object.hasOwn` does not traverse the prototype chain, and `JSON.parse` assigns keys like `"__proto__"` as ordinary own properties (not prototype mutation), so there's no pollution vector here even for a maliciously crafted `org-chart.json`.
- **`If-Match`/ETag concurrency** (`file-write-core.ts:60-84`, `orgMarkdownFileApi.ts:47-92`) — the fingerprint is computed from the actual file bytes at write time (`fileFingerprint(current)`), compared via `unquoteEtag(ifMatch)`, and a mismatch cleanly 409s with the server's current fingerprint echoed back for the client's conflict-resolution UI. The client correctly strips quotes on load and re-quotes on save. This is a standard, sound optimistic-concurrency pattern with no unusual race beyond the ordinary "two clients loaded the same version" case it's designed to catch.
- **`GET /api/org/file`'s lack of chart-membership gating** — initially looked like an inconsistency with the Stage-2 fix for the two `:leadId` GET routes, but it's explicit, documented design (`routes/org.ts:17-23`): it mirrors the pre-existing secret-gated route's same six-kind allowlist with no lead-membership concept (shared docs like `decision_log.md` have no "lead" at all), and dropping the secret for a loopback/tailscale-only caller is the stated, PO-approved relaxation. Not a new hole introduced by this iterate.
- **`useOrgChart`/`useOrgChartPresence`** (`client/src/hooks/useOrgChart.ts`, `useOrgChartPresence.ts`) — clean single-source-of-truth derivation; `"absent"` only fires on a confirmed `OrgChartMissingError`, matching AC-6a/6b/AC-7's stated contract. No ordering issue found.

## Summary

1 HIGH doubt (boundary & contract / reversibility — the charter-write chart-membership gate is bypassable via a URL-encoded trailing slash in `leadId`, letting an unauthorized write reach an orphaned/unregistered lead's `charter.md`) and 1 MEDIUM doubt (concurrency & ordering — `AuditLogModal`'s pagination can duplicate a page under rapid double-click, and silently swallows errors on any page after the first). Both are concrete, reproducible, file:line-cited, and neither was covered by the existing test suite (the closest existing test uses an unencoded probe string). Attempted disproof on the file-I/O guard chain, the `Object.hasOwn`/prototype-pollution angle, and the ETag concurrency contract came up empty — those mechanisms are sound as implemented. Per the advisory-must-address contract: the implementer must fix or write a reasoned rebuttal for both before commit.
